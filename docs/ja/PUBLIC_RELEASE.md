# リポジトリを公開する

GitHub の private リポジトリを public に切り替えるときの共通手順。公開前に確かめること、切り替え方、切り替えた直後に入れる GitHub の設定をまとめた。オーナーと、公開の準備をする Claude Code セッションが読む。使うときは[チェックリストの雛形](../../templates/PUBLIC_RELEASE.md)をプロジェクトにコピーし、[準備用のプロンプト](../../prompts/prepare-public-release.md)でセッションを始める。

> [!WARNING]
> 公開されるのは今のファイルだけでなく、履歴のすべてだ。一度コミットして後から消した秘密情報も読めてしまう。以下の確認は、見えるようになるブランチ、タグ、プルリクエストの ref をすべて対象にする。

## 役割分担

- Claude は調査とローカルでの確認、ファイルの下書きをし、結果をプロジェクトのチェックリストに記録する。
- 判断が要る項目の決定、push、GitHub の設定変更、公開範囲の切り替えはオーナーがする。Claude は手順を説明するだけで、自分では操作しない（`github-workflow.md`、`git.md`）。
- リポジトリの公開はデプロイではない。ただし、あるブランチへの push でデプロイされるプロジェクトなら、push のたびにそのことを伝える（`deployment.md`）。

## 1. 公開する範囲を決める

ローカルのブランチだけでなく、GitHub 上の ref をすべて一覧にする：

```bash
git ls-remote origin
```

- ブランチとタグ：どれを公開するかはオーナーが決める。公開しないものは、切り替える前に GitHub から消す。
- `refs/pull/<n>/head`：プルリクエストの head コミットは、ブランチを消しても force push しても GitHub に残る。これも一緒に公開され、消せるのは GitHub Support だけだ。
- 公開したいローカルのブランチは push 済みにしておく。そうすれば次のスキャンと同じコミットが対象になる。

## 2. 履歴をスキャンする

全履歴に秘密情報スキャナーをかける。標準は `gitleaks` だ（オーナーの承認を得てから Homebrew で入れる。プロジェクトの依存には加えない）：

```bash
gitleaks git --log-opts="--all" --redact .
```

スキャナーが拾わないものは手で確かめる：

| 確認すること | コマンド |
|---|---|
| コミットの author と committer | `git log --all --format='%an <%ae> / %cn <%ce>' \| sort -u` |
| AI の co-author 行 | `git log --all --format=%B \| grep -i co-authored-by` |
| これまでにコミットされた全ファイル | `git log --all --name-only --format= \| sort -u` |
| ローカルの絶対パス | `git log --all -p \| grep -nE '/Users/\|/home/'` |
| メールアドレス | `git log --all -p \| grep -noE '[[:alnum:]._%+-]+@[[:alnum:].-]+\.[a-z]{2,}' \| sort -u` |

期待する結果：

- author と committer はすべてオーナーの GitHub アカウントと、その `noreply` アドレスだけ。
- `.env*`（`.env.example` を除く）、`.dev.vars*`、ビルド成果物、ログ、ローカル設定のファイルは一度もコミットされていない。
- ローカルパス、個人のメールアドレス、その他の個人情報がない。

本物の秘密情報が見つかったら、漏れたものとして扱う。まずオーナーが無効化するか差し替える。履歴の書き換えにはオーナーの明示的な指示が要るし、書き換えても既存のクローン、フォーク、`refs/pull/*` には届かない。

## 3. 中身を見直す

秘密情報ではないが、公開に向かないかもしれないものを、今のツリーと履歴から探す。項目ごとに、残す・直す・消すをオーナーが決める。今ファイルを消しても履歴からは消えない。

- 識別子：クラウドのアカウント ID やリソース ID、内部のホスト名、サブドメイン。秘密情報ではなく、ビルドに必要なものだけ残す。
- 第三者の素材：引用した文章、画像、フォント、アイコン、ライセンスに制限のあるデータ、AI モデルの利用規約。
- 内部のメモ：`CLAUDE.md`、`prompts/`、検証ログ、障害の記録、引き継ぎメモ。計画や未解決のセキュリティ項目が書かれていることが多い。
- GitHub 側のデータ：Git には入っていないが、リポジトリと一緒に公開される。プルリクエストと Issue の本文やコメント、ワークフロー実行のログと成果物、リリースとその添付ファイル、Wiki。GitHub 上で確かめ、見せたくないものは消すか直す。

## 4. 見せ方を整える

- `LICENSE`：オーナーが選び、依存パッケージのライセンスと衝突しないか確かめる。
- `README.md`（と `README.ja.md`）：状態の記述を正しくし、クイックスタートが非公開のリソースなしで動くようにする。
- `SECURITY.md`：脆弱性が見つかりうるコードがあるなら、非公開の脆弱性報告への案内を置く。
- `CONTRIBUTING.md` と Issue・プルリクエストのテンプレート：外部からの貢献をオーナーが望む場合だけ置く。
- GitHub 上のリポジトリの説明とトピック（オーナー）。

## 5. 最終確認

- 公開するコミットでプロジェクトのテスト、lint、ビルドが通り、オーナーの push の後に CI が通っている。
- 依存の監査（たとえば `npm audit --omit=dev`）で、本番の依存に未解決の脆弱性がない。
- 最後のコミットに対して[手順 2](#2-履歴をスキャンする)のスキャンをもう一度かける。
- プロジェクトのチェックリストの全項目が、済み、理由付きの保留、対象外のどれかになっている。

## 6. 公開範囲を切り替える

オーナーが **Settings → General → Danger Zone → Change repository visibility → Make public** で切り替える。

## 7. 公開直後に GitHub の設定を入れる

GitHub Free では、public リポジトリでしか無料にならない保護がいくつかある。だから切り替えた直後に入れる。設定の名前は変わることがあるので、その時点の GitHub Docs と照らし合わせ、確かめた日付を記録する。

1. **Settings → Advanced Security**：非公開の脆弱性報告（Private vulnerability reporting）と、secret scanning の push protection を有効にする。secret scanning 自体は public リポジトリなら自動で動く。依存パッケージがあれば Dependabot alerts も有効にする。
2. **Settings → Rules → Rulesets**：デフォルトブランチへの force push と削除を禁止する ruleset を作る。CI があれば必須のステータスチェックも足す。bypass の一覧は、オーナーが必要としない限り空にしておく。ruleset があっても、ホスティング側の Git 連携による push からのデプロイは止まらない。
3. **Settings → Actions → General**：
   - ワークフローがない：Actions を無効にする。
   - ワークフローがある：使っている action だけを許可し、`GITHUB_TOKEN` のデフォルト権限を読み取り専用のままにする。外部の貢献者のプルリクエストからのワークフロー実行には承認を必須にする。
4. **Settings → General → Features**：Wiki、Projects、Discussions、Issues は、オーナーが使いたいもの以外オフにする。

## 8. 確認して記録する

- サインアウトしたブラウザでリポジトリを開き、意図したブランチとファイルだけが見えることを確かめる。
- 空のディレクトリから README のクイックスタートを試す。HTTPS での `git clone` が認証なしで通ること。
- **Security → Secret scanning** にアラートがないか確かめる。
- 入れた設定を日付付きでプロジェクトのチェックリストに記録し、README の状態を更新する。
